The shared release workflow checks the published version with `npm view --prefer-online`, each query bounded to 20 seconds and the whole wait to a ten-minute deadline: `npm view` otherwise answered from npm's own cache, which still held the package from before the publish, so data-cap 0.8.0's release was marked failed although npm served it. `displayPath` keeps a file inside the root whose folder or name starts with two dots (`..cache/x.ts`) relative. A benchmark report also cuts a path that follows `=` or `key:` from a failure's message, and escapes a `|` (and any backslash before it) in the failed-measurement cell so it cannot add a column. The README's `CodeRabbit` row names every case in which the check still fails. The shared `no-node-fs` rule also reports `node:fs` named by a template literal with no `${}` and loaded through `process.getBuiltinModule`, and the shared tsconfig loader reads the config through the filesystem it is handed and reports what the compiler rejects in it (still using the paths that parsed) instead of ignoring it, and a config it cannot read as a warning too. The re-exported packages move to `@maverickcer/env-cap` ^0.7.0 and `data-cap` ^0.8.0, the scaffolded and shared workflows pin setup-node v7.1.0, upload-artifact v7.0.2 and download-artifact v8.0.2, and dev tooling takes Dependabot's pending updates. A benchmark report no longer presents an overhead the run could not measure as zero: when the package's median is not above the baseline's, the summary says no overhead was measured and the throughput ceiling is "not measurable" instead of an infinite figure.
